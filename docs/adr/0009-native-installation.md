# ADR 0009 — Installing from inside each agent

Date: 2026-10-05 · Status: accepted.

## Why

shibaox-mem lives inside the agents; it is not an application. Up to 0.1.1 only Claude Code installed it as a plugin; in the others one had to download a binary and run `shibaox-mem install <agent>`. All four have a plugin or extension mechanism of their own, and that is where people expect to install from. Apple signing and `install.ps1` leave the to-do list: they only served whoever downloads files by hand.

## What exists

| Agent | Command | Where it is | How it reaches the binary |
|---|---|---|---|
| Claude Code | `claude plugin install shibaox-mem@shibaox-plugins` | repository root (`.claude-plugin/`, `hooks/`, `plugin/`) | `shibaox-mem.sh` |
| Codex | `codex plugin add shibaox-mem@shibaox-plugins` | `plugins/codex/` (`.codex-plugin/plugin.json`, `hooks/hooks.json`, `.mcp.json`) | `shibaox-mem.sh` |
| Gemini CLI | `gemini extensions install <repository>` | `plugins/gemini/`, packaged in the release | inside the archive (`bin/`) |
| OpenCode | `opencode plugin shibaox-mem-opencode --global` | `plugins/opencode/` (its own npm package) | `binary.js` |
| Cursor | Cursor's marketplace / import the repository | `plugins/cursor/` (`.cursor-plugin/plugin.json`, `hooks/hooks.json`, `mcp.json`) | `shibaox-mem.sh` |

Everything the agents read is generated by `scripts/plugins.ts` from one definition (name, version, each agent's events taken from the specs in `src/install/`), and is committed because the agents fetch it from git. A test fails if any file diverges from what the script would write.

## Decisions

- **One binary for every agent, in `~/.shibaox/mem/bin`.** One 63 MB copy instead of one per agent, and a stable path for `shibaox-mem ui`, `status` and `doctor`. The script only fetches it at session start, from the release of the plugin's version, with the checksum verified; **it never downgrades**, so that plugins of different versions in two agents do not keep swapping the binary on each other. A pre-release yields to the final version.
- **Gemini carries the binary inside.** Gemini's extensions install one archive per platform from the release (`{platform}.{arch}.shibaox-mem.tar.gz`); with the binary inside, there is nothing to download on the first session. `scripts/package-gemini.sh` produces the five in the release workflow.
- **OpenCode is a separate package, `shibaox-mem-opencode`.** An npm package only has OpenCode's tool API if it declares it as a dependency (measured: `import("@opencode-ai/plugin")` fails without it). Putting it in `shibaox-mem` would weigh on whoever only uses `npx shibaox-mem`. Registering the MCP server through the plugin's `config` hook was tried: the hook runs, but the server did not start.
- **Only one speaks.** Installed twice in the same agent (directly and as a plugin), the plugin's run stands down: it passes `--via-plugin`, and the binary leaves silently if that agent's direct-install file has our hooks. In OpenCode, the npm package stands down if the direct plugin file exists.
- **Codex 0.153 reads `.codex-plugin/plugin.json`.** With only a `plugin.json` at the root, it synthesises a manifest without a version. `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` are expanded in hooks and exist as environment variables (and so do the `CLAUDE_PLUGIN_*` aliases).

## Proven on this machine, in isolated HOMEs

| Agent | Install by the native command | Events seen in `hook_runs` |
|---|---|---|
| Claude Code (`--plugin-dir`) | yes | `session-start`, `prompt`, `session-end` |
| Codex (local marketplace → `plugins/codex`) | yes, version 0.1.1 in `plugins/cache/` | `session-start`, `prompt`, `session-end`; turn recorded as `codex` |
| Gemini (packaged archive) | yes, 4 hooks registered, MCP server connected | `session-start`, `session-end` |
| OpenCode (the package's tarball) | yes | `session-start`, `prompt` |
| Cursor | no Cursor to run | — |

## Proven with the published 0.2.0

With the README's commands, in isolated HOMEs, from the public repositories and release: Claude Code (`shibaox-plugins` → plugin 0.2.0), Codex (`shibaox-plugins` → `plugins/codex` at the tag, by `git-subdir`) and Gemini CLI (the release's `darwin.arm64.shibaox-mem.tar.gz` archive) install, fetch or bring the 0.2.0 binary and record `session-start`, `prompt` (where the agent gets there without a login) and `session-end`. The pre-release `v0.2.0-rc.1` served to prove the same before the final version, including Gemini's choice of archive by platform.

The `shibaox-plugins` marketplace serves both: `.claude-plugin/marketplace.json` for Claude Code and `.agents/plugins/marketplace.json` for Codex.

`doctor` recognises the native installs (and suggests the native commands when one is missing) from the version after 0.2.0.

## To confirm

- The Codex plugin's MCP server: declared as the documentation describes, but did not start in a session without a valid login.
- Turn end: Codex (`Stop`), Gemini (`AfterAgent`), OpenCode (`session.idle` with an answer) — all three need a model answering, which this machine does not have for them.
- Cursor: everything. The plugin follows the documentation; the marketplace listing is a submission by the account's owner.
- Windows: the Claude Code, Codex and Cursor plugins use `sh`; Gemini's and OpenCode's do not.
