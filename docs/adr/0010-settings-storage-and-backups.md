# ADR 0010 — M6: settings, the viewer at session start, storage and backups

Date: 2026-10-06 · Status: accepted.

## What exists

- **One settings file**, `<data dir>/env`: dotenv, 0600, keys named exactly like the environment variables, the environment winning over the file. Read by `src/settings/settings.ts` (environment > file > default, validation key by key, a public view where secrets are fingerprints) and written atomically by `src/settings/env-file.ts`, which keeps comments and lines it does not know. The viewer's **Settings** tab edits it (`GET/PUT /api/settings`).
- **The viewer opens when a session starts** (`SHIBAOX_MEM_UI_AUTO_OPEN`, on by default): the session-start hook starts `shibaox-mem ui --auto` detached; the viewer records itself in `<data dir>/ui.json` and decides whether to open a browser (`POST /api/open`).
- **The store can move** (`SHIBAOX_MEM_STORE_DIR`): the database and its backups live wherever the user put them from **Storage**; the binary, the settings, the logs and `ui.json` stay in the data directory.
- **Backups** (`SHIBAOX_MEM_BACKUP_TO`, `_EVERY_HOURS`, `_KEEP`, `_S3_*`): `shibaox-mem backup` and the **Backups** card; a hook starts one when it is due.
- **Collaborative mode — soon**: one card in Settings, text only.
- Also in this milestone: `SHIBAOX_MEM_TYPESAFE=off` (the key is kept, the heuristic judge works alone), `SHIBAOX_MEM_RETENTION_DAYS` (honoured by `compact`), `GET /api/doctor` and `POST /api/compact` for the viewer, generic leases in `src/store/meta.ts`.

## Decisions

- **The settings file is the existing `env` file, in dotenv.** Users had already written `TYPESAFE_API_KEY=` there by hand; a second format would have meant two files to explain. Values are written raw (no escaping) so that `C:\Users\…` and `\\nas\share` survive a round trip; a pair of quotes is dropped on reading; `export` is tolerated; `#` comments and unknown lines are kept where they are. `SHIBAOX_MEM_DATA_DIR` and `SHIBAOX_HOME` cannot live in the file — they are what locates it — and the viewer shows them read-only.
- **Secrets never leave through the API.** `publicSettings` reports `{set, fingerprint}` (the same `keyFingerprint` the breaker uses); a `PUT` takes a new value or `null`; validation messages never repeat a value. The file and `ui.json` are 0600; a `chmod` that fails (exFAT, vfat) is tolerated, because an external disk without permissions is still a place the user may choose.
- **Data directory ≠ store directory.** The plugin shims (`plugin/shibaox-mem.sh`, `plugins/*/`, `plugins/opencode/binary.js`, the npm shim) resolve `$data/bin` on their own; had the data directory moved, every one of them would have had to learn the new place. So only the database moves: `resolvePaths` returns `{dataDir, storeDir}`, `openDb` opens the store by default, and every process reads the `env` file on its next run (one small file read) and follows. `inspectTarget` tells what a target is — network share, filesystem without permissions, synced folder, a database already there — and the doctor keeps warning while the store sits on a network filesystem, where SQLite's locking is not reliable; backups to the NAS are the safe path.
- **A move holds writers off and copies, it does not stream.** A second connection takes `BEGIN IMMEDIATE` (the pattern `migrate()` already used), so no process can commit; `VACUUM INTO` on another connection takes the copy (`VACUUM` cannot run inside a transaction, hence two connections); the copy is checked (`quick_check`, same `user_version`, same count of memories) before the settings point at it; the old file is renamed `.moved-<time>` with its `-wal`/`-shm` beside it, never deleted. Hooks that meet the frozen database wait up to their `busy_timeout`, then fail open, which is what they do for any other lock. The viewer closes its own connection first (Windows cannot rename an open file) and reopens on the new store. A move is refused while a drain or backup lease is held, and the Storage card says when sessions were active in the last five minutes.
- **One viewer per machine, the server arbitrates.** The first draft put a lease in `meta`, refreshed on every request; that would have been a database write per click, contending with the prompt hook's 100 ms `busy_timeout`, and tied to a store that this same milestone lets move. Instead `ui.json` in the data directory records `{pid, origin, token, startedAt}`, created with `wx` so that two `ui --auto` racing leave exactly one on record (the loser probes the winner and asks it to open); a stale file is told apart by a probe (`GET /api/ping` with the token, 300 ms). The server alone decides whether to open a browser: not while a tab has pinged in the last 90 s (the page pings every 30 s and on becoming visible, and says goodbye on `pagehide`), not twice within 10 s. The heartbeat is a request, so it also keeps the idle timer alive: a viewer with a tab open does not stop after 30 min.
- **The hook pays for one file read and one spawn, nothing else.** `spawnViewer` runs only on `session-start` (not `resume`), reads the settings, and starts `ui --auto` detached with stdio ignored; it stays silent under `CI`, over SSH (`SSH_CONNECTION`, `SSH_TTY`) and on Linux without `DISPLAY`/`WAYLAND_DISPLAY`. `SHIBAOX_MEM_UI_BROWSER=none` keeps the browser closed, for tests. The perf budgets test runs with auto-open off, like distill; the live run measured 5–14 ms for a warm session-start on an empty store and 43 ms on the 206 MB one.
- **Backups are snapshots, taken by the hooks with time to spare.** Only `turn-end` and `session-end` (1000 ms budgets) start one, and only when `backupDue` says so from `meta.backup.last`; `prompt` and `session-start` never do. `VACUUM INTO` gives a consistent copy whatever the other processes are doing; the copy is gzipped through `node:zlib` streams — `CompressionStream` hangs on some Bun versions, found the hard way — and sent to a folder (copy to `.part`, then rename) or to an S3-compatible bucket through `Bun.S3Client` (no SDK; `endpoint` for R2, MinIO, B2; multipart upload from a file). Names are `shibaox-mem-<UTC time>-v<schema>.db.gz`; only those are listed and pruned, so a bucket or folder shared with anything else is left alone. One target key, `SHIBAOX_MEM_BACKUP_TO`, is a folder or `s3://bucket/prefix`; the four `S3_*` keys only matter for the latter.
- **Restoring checks before it replaces.** The copy is fetched, unpacked, opened read-only and checked (`quick_check`, `user_version` not newer than this binary, a `memories` table) before the database is frozen and swapped; the current file is kept as `.replaced-<time>`, side files with it. A copy from a newer shibaox-mem is refused with the advice to upgrade.
- **Leases are generic, and a dead owner does not count.** `leaseActive`/`claimLease`/`releaseLease` take a key; drain, backup, move and restore exclude one another. Owners name their process (`<pid>-<uuid>`, `ui-<pid>`); a lease whose process no longer exists is ignored, so a backup killed mid-way does not block the next for ten minutes. An owner that names no process is trusted until the lease expires.
- **Collaborative mode is one card, and nothing else.** The design criticises claude-mem's funnel (a banner every session, a button in the viewer); this card is the only mention, carries no link, no waiting list and no date, and says plainly that this build contains no client for it. The text commits to what will not change — local first, opt-in per project, nothing leaves the machine until turned on, no telemetry — and to the one fact that makes the feature possible: the project key is already the normalised git remote, the same in every clone.
- **`vue-tsc` stays out; the viewer's forms are plain Nuxt UI.** First uses of `USwitch`, `UAlert` and `UModal` for confirmations; every card is a `Card.vue` in the Overview's panel style.

## Measurements

| What | Result |
|---|---|
| Session-start hook with auto-open on (spawn of `ui --auto`), empty store, warm | 5–14 ms; 67 ms on the very first run (database created) |
| Session-start hook on the real store (206 MB, 67 000 memories), last 3 hours | 43 ms average, 51 ms max |
| `VACUUM INTO` of the real store (206 MB) to a local temp dir | 200 MB in 1.3 s |
| gzip of that copy (`node:zlib`) | 68 MB in 1.9 s |
| Settings file read (`readEnvFile`) | below 1 ms; one read per hook |
| Tests | 988 passing, 1 skipped (56 files) |
